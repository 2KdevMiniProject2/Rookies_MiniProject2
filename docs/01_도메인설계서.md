## 1. 도메인 개요

소규모 매장(카페, 베이커리, 분식점 등)을 운영하는 사장님이 온라인으로 메뉴를 등록하고, 손님이 앱/웹에서 메뉴를 확인한 뒤 **픽업 시간을 지정해 미리 주문**하는 테이크아웃 전용 예약·주문 관리 서비스다. 전화 주문이나 매장 내 대기 없이, 손님은 원하는 시간에 맞춰 주문하고 사장님은 들어온 주문을 수락/거절하며 준비 상태를 관리한다.

서비스에는 세 종류의 사용자가 존재한다.

- **손님(USER)**: 매장과 메뉴를 둘러보고 주문하는 일반 회원
- **사장님(OWNER)**: 매장을 등록하고 메뉴·주문을 관리하는 회원
- **관리자(ADMIN)**: 전체 회원을 조회·관리하는 운영 역할. 회원가입으로는 생성할 수 없고 시드 데이터로만 존재한다.

## 2. 핵심 도메인 객체

| 도메인 객체 | 설명 |
|---|---|
| **User (회원)** | 로그인 주체. `role`(USER/OWNER/ADMIN)로 권한이 구분된다. |
| **Store (매장)** | 사장님이 등록하는 가게. 한 사장님이 여러 매장을 가질 수 있다(1인 다중 매장). |
| **StoreDetail (매장 상세)** | 영업시간(오픈/마감) 등 매장의 부가 정보. 매장과 1:1 관계. |
| **MenuItem (메뉴)** | 매장에 속한 판매 품목. 품절 여부를 가진다. |
| **Order (주문)** | 손님이 특정 매장에 대해 생성하는 주문. 픽업 시간과 상태를 가진다. |
| **OrderItem (주문 항목)** | 주문에 담긴 메뉴 한 줄. 주문 시점의 가격·수량을 기록한다(메뉴 가격이 나중에 바뀌어도 과거 주문 금액은 변하지 않음). |

## 3. 도메인 관계도

```
User (1) ──── (N) Store        : 사장님(OWNER)이 매장을 소유
Store (1) ──── (1) StoreDetail : 매장의 영업시간 상세
Store (1) ──── (N) MenuItem    : 매장이 등록한 메뉴
User (1) ──── (N) Order        : 손님(USER)이 생성한 주문
Store (1) ──── (N) Order       : 매장이 받은 주문
Order (1) ──── (N) OrderItem   : 주문에 담긴 메뉴 항목들
MenuItem (1) ──── (N) OrderItem: 주문에 포함된 메뉴
```

물리적인 컬럼·타입 수준의 ERD는 `Entity 설계서`에서 별도로 다룬다.

## 4. 비즈니스 규칙

### 4.1 권한/역할 규칙
- 회원가입 시 `ADMIN` 역할은 선택할 수 없다 (권한 상승 방지). `ADMIN`은 시드 데이터로만 생성된다.
- 매장 등록/수정/삭제, 메뉴 등록/수정/품절전환/삭제, 메뉴 이미지 업로드는 **OWNER 역할**만 가능하다.
- 역할이 OWNER라도 **본인이 소유한 매장/메뉴가 아니면** 수정·삭제할 수 없다 (역할 검증과 소유권 검증은 별개 — 둘 다 통과해야 함).
- 회원 정보 조회·수정·탈퇴는 **본인 계정만** 가능하다.
- 전체 회원 목록 조회는 **ADMIN 전용**이다.

### 4.2 공개/비공개 규칙
- 매장 목록·상세, 메뉴 목록은 **로그인하지 않아도** 조회할 수 있다 (둘러보기 가능).
- 그 외 쓰기 작업(주문, 매장/메뉴 등록·수정·삭제, 이미지 업로드)은 로그인(JWT 인증)이 필요하다.

### 4.3 삭제 규칙
- `User`, `Store`, `MenuItem`은 **소프트 삭제**를 사용한다 (`deletedAt` 타임스탬프 기록, 실제 row는 지우지 않음). 주문(`Order`)이 `User.customer`/`Store`를 FK로 참조하고 있어서, 주문 이력이 있는 계정·매장을 하드 삭제하면 FK 제약 위반이 나기 때문이다.
- 탈퇴한 회원의 이메일은 (unique 제약으로) 같은 이메일로 재가입할 수 없다. 재가입 정책은 별도 논의 필요.

### 4.4 주문 규칙
- 품절(`soldOut = true`) 메뉴는 주문에 담을 수 없다.
- 주문 상태는 다음 흐름만 허용되는 단방향 상태 머신이다.

```
PENDING(접수대기) ──accept──▶ ACCEPTED(준비중) ──ready──▶ READY(준비완료) ──complete──▶ COMPLETED(픽업완료)
       │
       ├──reject──▶ REJECTED(거절)      [사장님]
       └──customerCancel──▶ CANCELLED(취소)  [손님, PENDING 상태에서만]
```
- 정의되지 않은 상태 전이(예: READY에서 다시 PENDING으로)는 모두 거부된다 (409 Conflict).
- 주문 항목(`OrderItem`)의 가격은 **주문 생성 시점의 메뉴 가격을 그대로 복사**해서 저장한다 — 이후 메뉴 가격이 바뀌어도 과거 주문 금액에는 영향이 없다.

### 4.5 이미지 업로드 규칙
- 메뉴 이미지는 OWNER만 업로드할 수 있다.
- 업로드되는 파일은 서버가 정한 허용 목록(JPEG/PNG/WEBP)의 Content-Type만 허용하며, 클라이언트가 보낸 원본 파일명은 저장 경로/확장자 결정에 사용하지 않는다 (서버가 직접 확장자를 매핑).

## 5. 용어 정의

| 용어 | 정의 |
|---|---|
| 사장님 (OWNER) | 매장을 소유하고 메뉴·주문을 관리하는 역할 |
| 손님 (USER) | 매장을 둘러보고 주문하는 일반 회원 |
| 관리자 (ADMIN) | 전체 회원 관리 권한을 가진 운영 역할. 가입으로 생성 불가 |
| 소프트 삭제 | DB row를 실제로 삭제하지 않고 `deletedAt`에 삭제 시각을 기록해 "삭제된 것으로 취급"하는 방식 |
| 소유권 검증 | 요청을 보낸 사용자가 대상 리소스(매장, 메뉴, 계정 등)의 실제 소유자인지 서버가 직접 확인하는 절차 (클라이언트가 보낸 ID를 그대로 믿지 않음) |
| IDOR (Insecure Direct Object Reference) | 클라이언트가 보낸 값(다른 사람의 id 등)을 서버가 그대로 신뢰해서, 권한 없는 사용자가 다른 사람의 리소스에 접근할 수 있게 되는 취약점 |
| JWT (JSON Web Token) | 로그인 성공 시 발급되는 토큰. 이후 요청마다 이 토큰으로 "누가 보낸 요청인지"를 서버가 판별한다 (세션 저장 없이, STATELESS) |
| N+1 문제 | 목록 1건을 조회했는데 연관 데이터를 각 건마다 추가로 조회해서 총 N+1번의 쿼리가 나가는 성능 문제. 본 프로젝트는 `JOIN FETCH`/IN절 배치 조회로 해결함 |
